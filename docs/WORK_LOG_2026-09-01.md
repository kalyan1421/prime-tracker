## Part 1 — Product fixes (commits `5a7e8ed` → `066ba38`)

### 1.1 Delete a mistaken record from a unit's history — `5a7e8ed`, `066ba38`

**Problem.** The delete flow and its Founder-approval gate already existed, but were mounted only in Rent History and in `SoldUnitPanel`. `SoldUnitPanel` renders only the *first* closed sale, so a unit imported twice had duplicate rows on its timeline that no screen in the application could delete. Separately, the trash icon appeared only on rows tagged *Historical*, so a lease recorded live had no delete affordance at all — the timeline looked broken rather than principled.

**Delivered.**
- An inline delete control on **every** lease and sale row of the timeline, which is where duplicates are actually noticed.
- New `TimelineRecordDelete` component keeps the two record kinds on different rules: a **backfilled** record still goes through the Founder gate (its ledger was typed in from paper and cannot be rebuilt); a **live** record takes a confirmation (it can be re-entered from its own terms).
- The live confirmation leads with what does *not* happen: a delete is a soft delete and does **not** change the unit's status. Deleting a lease to free a unit leaves it reading `LEASED` with no tenant. The dialog names **End tenancy** (or **Cancel**, for a sale) as the tool that was actually wanted.
- Permission is checked before the icon renders (`lease:edit` / `sales:edit`); the server's own rules still stand on top, and a refusal now surfaces as a toast instead of a silent no-op.
- The approval gate itself is unchanged — this widens *who can reach* the flow, not *who can decide*.

### 1.2 Sale import no longer writes rows it already has — `5a7e8ed`

**Problem.** The rent importer has compared rows against stored leases since it was written. The sale importer never did, and had no DB exclusion constraint underneath it either (a sale carries no date range). A re-uploaded sheet came back **entirely green** and wrote every previously-imported row again.

**Delivered.** Identity is `(unit, buyer, closing day)`, checked in three places:
- the **preview** marks such rows `duplicate` rather than `error` — they are correct, just already done;
- the **commit** re-checks before each write, so a stale preview cannot slip past;
- `backfillSale` refuses outright, covering the manual form and any direct call.

### 1.3 Lease UI on a SOLD unit — `5a7e8ed`

The API never blocked this; the web app hid the whole Tenant card. Units that reached the state anyway (hand-flipped status, a tenancy outliving the sale, a backfill entered out of order) could not be looked at or corrected, while the timeline went on warning about it and naming controls that were not on the page. Billing rules are untouched — `NOT_ON_SOLD_UNIT` still keeps these leases out of rent roll, invoicing, cash flow and dunning. The warning previously said the tenant "may still be being billed", which was never true and sent people hunting for money that was never moving; it now says what is actually wrong.

### 1.4 Unit checklist: pick stages instead of typing them — `5a7e8ed`, `b40bd54`, `d2ea996`

**Problem.** The stage name was free text. That is how one unit gets "Store Front Glass", the next "Storefront glass", and a rollup that can never group them. The first fix offered the building's own template — but templates are configured per building, so on a unit whose building had five stages (four already on it) the picker offered exactly **one**, while the full eighteen-stage list Prime actually works from sat on three units one building over, unreachable.

**Delivered.**
- The pickable set is now the **union**: this building's template, plus every stage label already in use on any unit the caller can see. Same unit, same screen: **1 option became 38**.
- Drawn from stages *in use* rather than a curated catalogue — nothing to seed, nothing to maintain; the first person to type a stage makes it available everywhere, and a name nobody uses stops being offered. The trade is that a typo becomes selectable, so each row carries its usage count ("on 1 unit" next to "on 40 units"), which is what tells them apart without anyone policing a list. The building's own template still sorts first under its own heading.
- Scoped like `getProjectRollup` — a role that only sees its own projects only sees stage names from them.

### 1.5 Checklist: add in bulk, and reorder — `b40bd54`

- **Add many at once.** The picker was single-select, so seeding a seventeen-stage template meant seventeen trips through the modal. It is now a checkbox list with *Select all*, posting **one** request. That is not an optimisation: the API throttles at 10 req/sec, so a frontend loop over the single-stage route would land about half a template and leave a checklist that *looks* complete and is not. Labels already on the unit are skipped rather than rejected.
- Per-stage fields (owner, status, inspection, dates) now appear only on the single-stage path — one inspection date applied to seventeen stages is not a shortcut, it is seventeen wrong dates.
- **Reorder.** `sortOrder` has always decided reading order and nothing could change it — moving a stage meant deleting and re-adding it, throwing away its status, dates and notes to fix nothing but position. Arrows rather than drag, because this table scrolls sideways and is read on a phone on site. The endpoint takes the **complete ordered list**, so the server never guesses what happens to the rows between, and two people reordering at once collide loudly instead of interleaving into an order neither asked for.

### 1.6 Site Tracker: the right action, visible to the right role — `5a7e8ed`, `b40bd54`, `bcfe662`

**Problem.** The grid deliberately lists only units with site work recorded against them — about **14 of 636**. Its only top-level button was **"New unit"**, gated on `unit:edit`, which CONSTRUCTION does not hold. So the visible action was the wrong verb *and* invisible to the role that lives on that page — and it is the button people pressed when they meant "track this one", which is how duplicate units got made.

**Delivered.** One header action: **Track an existing unit**, a stage picker over the building's template with everything preselected (untick what this fit-out does not need). Seeding stages is what puts a unit on the tracker. A building with no template says so instead of offering an empty list; that path now reads the wider stage library too, since template-less buildings are exactly the units the action exists to bring on. "Add stage" was dropped from the header — expanding a row does it better, with the unit's own checklist in front of you. Units are still created in Project Details.

### 1.7 Add Sale captures the whole deal — `bcfe662`

**Problem.** Add Sale asked for five things (buyer, price, deposit, closing date, notes) while the historical-sales import captured fifteen. A deal typed in by hand lost the seller, the broker, the agreement date and when the money was due — and nothing on screen said whether those were unknown or simply never asked. Sharpest edge: `Sale.seller` has existed on the model and been accepted by `backfillSale` since R4, but was on **neither** the create nor the update DTO, so anything typed into a manual sale was silently discarded by validation.

**Delivered.** Both paths now record the same facts.
- Unit, Building and Sqft are shown as **context**, not fields — the modal opens from the unit.
- **Price PSF** is derived (price ÷ sqft) and read-only: a field for it is only a way for the two to disagree. The import does not store it either.
- **Deposit** and **Second payment** become real installments on the sale's existing payment schedule rather than two more columns on `Sale`. They are created `DUE`, not paid — the form asks when a payment is *dated*, not whether the money arrived. Marking it paid is one click on the schedule. If an installment fails, the sale is already saved, so it warns by name instead of reading as a lost deal.
- **Broker** is a picker, not the import's free-text name match — here the real broker is one click away and a typo would produce no attribution at all.

### 1.8 A sale could never satisfy its own closing gate — `fa32c0c`

**Problem — the most serious of the batch.** The `CLOSED` gate refuses a sale whose Deed, NOC and Possession Certificate are not attached, and tells you to "upload them to the sale's documents, then move the stage". **There was no such place.** The gate counts `document.saleId`; the upload DTO had no `saleId`, `DocumentsService.create` never wrote one, and `GET /documents` could not even list by sale. The column the gate reads could not be set by any route in the application — so **every sale was permanently one step from closing**, and Sales could read exactly why a deal would not close and do nothing whatsoever about it.

**Delivered.**
- `saleId` accepted on upload and listable.
- A sale-attached document is **also** attached to that sale's unit and project — the columns are independent, not exactly-one-of. A Deed is evidence about the deal (what the gate asks) *and* about the unit (what whoever opens A-103 next year asks, not knowing which sale it arrived on). Filed in only one, the other audience never finds it.
- Unit and project are **derived from the sale**, not trusted from the caller — a mismatched `unitId` would file a Deed against the wrong unit, and the sale already knows the answer.
- Reading is scoped to `saleId` alone even though every such row also carries the unit: a unit that sold twice must not let the first deal's Deed answer for the second.
- The upload control sits in the **Edit Sale** dialog, one row per required category, appearing only when the chosen stage actually owes something, charged per rung *crossed* (a sale already Under Contract owes three to close, not five). It belongs where the refusal is read.
- **Verified end to end:** with the three attached, the refusal changes from the document gate to the discount gate — a different guard, correctly still standing.

## Part 2 — Deployment and infrastructure (commits `d5582a5` → `0ffe4a9`)

### 2.1 The old deploy job could never have worked — `d5582a5`

`security.tf` allows port 22 from `var.admin_cidr` — **one address, a home IP**. GitHub's hosted runners get a different address every run, so the `scp` step would have hung until its 20-minute timeout. Nobody hit it because `DEPLOY_ENABLED` was never set and the job reported *skipped* across 30+ pushes; arming it would have turned a silently-skipped job into a silently-hanging one. Widening 22 to GitHub's published ranges means thousands of addresses, re-published without notice, on the port that grants a shell.

**Delivered — release over SSM. The runner no longer connects to the box at all.**
- It uploads the build to S3 and calls `ssm:SendCommand`; the agent already on the instance pulls the artifact and releases it — reaching outward rather than being reached. The instance role has carried `AmazonSSMManagedInstanceCore` since it was written; the capability was there, unused.
- **Credentials are GitHub OIDC**, not stored access keys — a short-lived token minted per run. `EC2_HOST`, `EC2_SSH_KEY` and `GH_DEPLOY_TOKEN` are no longer used.
- The release script is **its own SSM document**, not `AWS-RunShellScript`. The role can then be permitted to run *this* script and nothing else; `SendCommand` on `RunShellScript` is "execute arbitrary commands as root", which is a much larger thing to hand a CI system. Parameters are `allowedPattern`-anchored because they are interpolated into a command running as root, and `SendCommand` is scoped to one document and one instance.
- Two things the old job got wrong, fixed: `send-command` returns as soon as a command is **accepted**, so the workflow now polls to completion instead of going green on a deploy that has not run; and the box's stdout/stderr is printed **even on failure**, because a red job with no log is a red job nobody can act on. The health check now fails the deploy, so a process restarting into a crash loop cannot report success.
- Port 22 becomes optional (`enable_ssh`, default true — flip off once a deploy has succeeded). Session Manager already gives a shell with no inbound port.
- New docs: `DEPLOY_SSM_SETUP.md` (setup, verification, rollback, known limits) and `RELEASE_2026-09-01.md`.

### 2.2 Any `terraform apply` would have destroyed the production server — `2b75761`

Found while planning the deploy-role change against the live account (`056836825737`). **The plan proposed rebuilding the only production server.**

- `data.aws_ami.ubuntu` is `most_recent = true`, and Canonical publishes a new 22.04 image every few weeks. The AMI id drifts with **no change to this repository**, so the *next* apply — whatever it was for — plans `aws_instance.api` as delete/create. Measured: a plan whose only intended change was an IAM role also proposed `ami-06e78a71af43ef21a → ami-040dc3b259ece28c6`. `disable_api_termination` would not have saved it — Terraform attempts the termination, fails, and leaves the apply half-finished. `user_data` had drifted too (the nginx proxy-buffer fix), and `user_data` only applies on first boot, so keeping it in the diff buys nothing and costs a replacement.
- Both are now ignored. Replacing the instance stays possible and becomes deliberate: `terraform apply -replace=aws_instance.api`.
- **Second finding, same plan:** `GOOGLE_CLIENT_ID` is a `SecureString` in the live account and the file still called it `String`, so every plan proposed **downgrading** it. `ignore_changes` covers value, not type, so it could not have been caught there. Moved to the secure list **with a `moved` block** — without one, Terraform reads it as destroy-then-create and the new parameter is born holding the literal `REPLACE_ME`, silently breaking Google sign-in.
- The RDS password diff in the same plan was state drift, not a real change (verified without printing the credential).
- **Result: plan went to 7 create, 1 change, 0 destroy. Applied. The API answers `/api/health` 200 and the SPA serves.**

### 2.3 Two real deploy failures, diagnosed and fixed — `9ca6eff`, `1560e61`

- **Failure 1 — `sts:AssumeRoleWithWebIdentity` not authorized.** The moment a job declares `environment:`, GitHub changes the OIDC subject claim from `repo:OWNER/REPO:ref:refs/heads/BRANCH` to `repo:OWNER/REPO:environment:NAME`. The trust policy pinned the *ref* form, which this job can never present. The branch restriction is not dropped — it moves to where GitHub actually enforces it: the `production` environment now carries a deployment branch policy allowing only `main`, checked before the token is minted. The two are a pair, noted at the condition.
- **Failure 2 — `set: Illegal option -o pipefail`, exit 2, before a single line ran.** `aws:runShellScript` writes the steps to `_script.sh` and runs it with `/bin/sh`, which on Ubuntu is `dash`; `pipefail` is a bashism. Top level is now POSIX `set -eu`; the real work already runs inside a `sudo … bash` heredoc, which keeps `pipefail` where it belongs. Also recorded *how it got through*: the pre-flight check ran `bash -n` on the extracted script, which validates a bashism happily. It now runs `sh -n` and `dash -n` too — though neither would have caught this either, since `set` is a runtime builtin, so the grep for top-level `pipefail` is the part that actually holds.

## Part 3 — In flight (uncommitted at end of session)

### 3.1 Fix blocked import rows in place, on both importers

Previously a sheet with a bad or missing cell had to be corrected in Excel and re-uploaded. Now the **Status cell renders an input** for the field the row is actually waiting on.

- **Rent history:** correctable `unitNumber`, `building` (an explicit clear, for sheets that prefix the project name — "Centro Plaza - Building 2" never matched the building's real name), `tenantName`, plus the existing dates/broker fields.
- **Sale history:** the same treatment over closing date, price, broker and unit. Optional payment/commission fields are deliberately *not* offered — a row is never blocked on them.
- **Fill-all:** where two or more rows are blocked on the same field, one control fills every one of them (still editable per row). A sheet that omits a column omits it for all 38 rows, and fixing that 38 times by hand is not a review.
- **Honest counts:** rows blocked by something no input can fix — a combined "812, 814" reference, a unit that has to be created first — are counted separately, so the fixable tally does not overstate itself. The "create the missing unit/building" flow is untouched and is still the right answer when the unit genuinely does not exist.
- Overrides arrive as JSON text on a multipart body and are **re-validated field by field** server-side, so a malformed client payload cannot reach `.trim()` or overwrite a good sheet value with an object.
- The preview now also chips **"N already imported"** alongside the blocked count.

### 3.2 Sessions no longer end for the wrong reasons

Two failures, both seen in real sessions at the 15-minute access-token mark:

1. **The server rotates refresh tokens** — using one revokes it. Two tabs each hold their own copy in memory, so the tab that refreshes second presents a token the first tab already spent, gets a 401, and would be logged out of a perfectly live session. The newer token is sitting in `localStorage`; the client now uses it instead. A `storage` listener rehydrates the auth store in the *other* tabs, which also makes "log out" and "log in as someone else" propagate correctly.
2. **Only an actual auth rejection ends a session.** A network blip, a 502 while the API restarts, a laptop waking up, a 429 — none of those say anything about the refresh token, and destroying the session over them is how a user gets thrown back to the login screen for no visible reason. Only a 401/403 on the refresh itself (`SessionEndedError`) logs out now; anything else leaves the session in place and the next request retries.
