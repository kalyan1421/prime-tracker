# Release — 2026-09-01

Six commits, `07b2947..066ba38`, merged to `main`. **2412 API + 97 web tests green**,
including the integration suite against a real Postgres on the CI runner.

**No Prisma schema changes and no migrations.** Application code only — the deploy is a
build-and-restart with nothing to run against the database. Two columns this release finally
uses (`Sale.seller`, `Document.saleId`) already existed and had simply never been written to.

A theme worth stating up front: **most of what was reported as missing already existed and
was merely unreachable** — a component never mounted, a column no endpoint would write, a
picker pointed at a data source almost nobody had populated. Check whether a feature is
unmounted before building it again.

## 1. Deleting a wrong record from a unit's history

**Reported:** "give icon i want delete option i have mistake add details History" — a unit
showed the same backfilled sale three times with no way to remove any of them.

**What was actually wrong.** The whole deletion flow existed — request → Founder approval →
delete, with `HistoricalRecordControls` built and tested — and was mounted in exactly two
places: the Rent History section (leases) and `SoldUnitPanel` (sales). `SoldUnitPanel`
renders only the **first** closed sale (`u.sales.find(...)`), so on a unit imported twice
the second and third duplicates had **no delete path anywhere in the UI**.

**Now:** every lease and sale row on the History timeline carries a delete control, because
the timeline is where a wrong row is actually noticed.

Two kinds, two rules:

| Record | Rule | Why |
|---|---|---|
| **Backfilled** (`isHistorical`) | Founder approval — request, decide, then delete | Its ledger was typed in from paper the system never witnessed; it cannot be rebuilt |
| **Live** | A confirmation | It can be re-entered from its own terms |

The live confirmation leads with what does **not** happen, which is the part people get
wrong: a delete is a **soft delete and does not touch the unit's status**. Deleting a lease
to "free up" a unit leaves it reading `LEASED` with no tenant — the exact broken state the
history banner then complains about. The dialog names **End tenancy** (or **Cancel**, for a
sale) as the tool that was actually wanted.

Scoping this to backfilled rows only was the first attempt and was wrong: a tenancy typed in
by mistake yesterday is exactly as wrong as one imported twice, and a timeline where some
rows have the button and others do not reads as broken rather than principled.

*Files:* `TimelineRecordDelete.tsx` (new), `HistoricalRecordControls.tsx` (gained an
`inline` variant), `UnitDetailPage.tsx`.

## 2. Sale import no longer writes rows it already has

**Reported:** "when i use import features data is getting duplicated on same unit when i try
to upload other unit details."

**Root cause — a real data-corruption bug.** The rent importer has compared incoming rows
against stored leases since it was written (`lease-import.service.ts:769-940`). The **sale
importer never queried `prisma.sale` at all.** A re-uploaded sheet came back entirely green
`ready` and wrote every previously-imported row again. Unlike a lease, a sale carries no date
range, so there is **no DB exclusion constraint underneath** to catch what the preview missed.
Three commits of the same sheet = three identical sales.

**Fixed at three layers**, identity being `(unitId, buyer case-insensitive, closing day)`:

1. **Preview** marks such rows `duplicate` — a status distinct from `error`, because the row
   is correct, there is simply nothing to do with it. Calling it an error pushes people to
   "fix" rows that are already right.
2. **Commit re-checks before each write.** This is the one that matters: the preview is
   advisory, and the actual trigger was a *stale* preview — "create the missing units and
   re-check the file" hands back a preview in which already-imported rows are green again.
3. **`backfillSale` refuses outright**, covering the manual form and any direct API call.

Also: a warning when the stored price disagrees with the sheet's (skipping in silence would
leave the wrong number in the books), and detection of the same sale listed twice *within*
one file — common on combined-deal sheets.

*Verify:* upload the same sale-history sheet twice. The second run should report
`N already imported` and import 0.

## 3. Lease UI on a SOLD unit

**Reported:** "after sold i need fill details lease detail that this is edge cases."

**The API never blocked this.** The web app hid the entire Tenant card when
`status === 'SOLD'`. Units reached that state anyway — a hand-flipped status, a tenancy
outliving the sale, a backfill entered out of order — and then had no way to be looked at or
corrected, while the history timeline went on warning about it and naming controls that were
not on the page.

**Now:** the Tenant card renders on SOLD units with its add/edit/end controls, plus a
standing note that a tenancy recorded there is kept for the record.

**Billing is deliberately unchanged.** `NOT_ON_SOLD_UNIT` still keeps these leases out of the
rent roll, invoicing, cash flow and dunning (~10 call sites). Recording a tenancy is a data
need; billing a tenant on a unit Prime no longer owns is a money decision with five
unanswered client questions behind it in `SALE_ON_TENANTED_UNIT_SPEC.md`.

**One warning was simply false.** It said the tenant "may still be being billed" — never true,
since `NOT_ON_SOLD_UNIT` excludes them from invoicing. It sent people hunting for money that
was never moving. It now says what is actually wrong: the two records disagree.

## 4. Construction stages — pick from a library, in bulk, in any order

**Reported:** predefined stages instead of free text; "i want 18 stage here to select and
custom stage"; multi-select; reordering.

### The picker was pointed at the wrong data

Stage lists are configured **per building** (`ConstructionStageTemplateItem`). Most buildings
have none. On the reported unit the building had five stages, four already used — so the
picker offered **one**, while the full eighteen-stage list Prime actually works from (01 Soil
Compaction … 17 Store front glass) sat on three units one building over, unreachable.

**Now** the pickable set is the **stage library**: the building's template *plus every stage
label already in use on any unit the caller can see*. Same unit, same screen: **1 option → 38**.

Drawn from stages *in use* rather than a curated catalogue, so there is nothing to seed and
nothing to maintain — the first person to type a stage makes it available everywhere, and a
name nobody uses stops being offered. The trade is that a typo becomes selectable, so each row
shows how many units run it: "on 1 unit" next to "on 40 units" is what tells them apart. The
building's own template still sorts first, under its own heading.

Scoped like `getProjectRollup`: a role that only sees its own projects only sees stage names
from them.

### Bulk add is mandatory, not a nicety

`POST /construction-checklist/unit/:id/stages` takes `labels[]` and writes them in one
request. **The API throttles at 10 requests/second**, so a frontend loop over the single-stage
route would land about half a seventeen-stage template and leave a checklist that *looks*
complete. Labels already on the unit are skipped, not rejected — ticking one twice is a slip,
not a reason to lose the other sixteen.

Per-stage fields (owner, status, inspection, dates) appear only on the single-stage path. One
inspection date across seventeen stages is not a shortcut; it is seventeen wrong dates.

### Reordering

`PATCH /construction-checklist/unit/:id/stages/order` takes the **complete** ordered id list.
A partial list is refused: it would have to invent positions for the rest, and two clients
each sending half would interleave into an order neither asked for. Two passes through a
negative range so no two rows collide mid-move.

Arrows, not drag-and-drop: the grid scrolls sideways and is read on a phone on site, where a
drag competes with the scroll. Before this the only way to move a stage was to delete and
re-add it — throwing away its status, dates and notes to change its position.

## 5. Site Tracker: one action, and it is the right one

**Reported:** "in site tracker i want to add new unit that existing … not to create a new
unit", then "remove this both buttons".

The page's only top-level button was **New unit**, gated on `unit:edit` — a permission
**CONSTRUCTION does not hold**. So the one visible action was both the wrong verb for the
everyday job and invisible to the role that lives on the page. It is how duplicate units got
created: people pressed it meaning "track this one".

**Now** a single **Track a unit** action: pick a unit that exists but is not on the tracker,
choose which stages to seed (all preselected, untick what this fit-out does not need), done.
Seeding stages is what puts a unit on the tracker — a unit counts as tracked once it has any
site work recorded.

"Add stage" and "New unit" were removed at your request. Units are still created in Project
Details, where the rest of a unit's details are set.

Also fixed: a unit with no stages used to dead-end at *"No checklist on this unit yet. Apply
one from the unit page"* — on the screen the site team actually works from.
`UnitConstructionChecklist` has always rendered its own empty state with Apply-template and
Add-stage on it; it was simply never reached.

## 6. Add Sale captures the whole deal

**Reported:** "for sale input i want all input details" + the fifteen-column list.

Add Sale asked for five things; the historical-sales import captured fifteen. A deal typed in
by hand lost the seller, the broker, the agreement date and when money was due — and nothing
said whether those were unknown or never asked.

**`Sale.seller` was a real bug.** It has been on the model and accepted by `backfillSale`
since R4, but was on **neither the create nor the update DTO** — so anything typed into a
manual sale was silently discarded by validation. Imported sales had a seller; hand-entered
ones could not.

Now: Seller, Buyer, Purchase Price, Price PSF, Deposit Amount + Date, Second Payment Amount +
Date, Sale Agreement Date, Closing Date, Broker, Notes — plus Unit / Building / Sqft as
read-only context (the modal opens from the unit; asking which unit would be asking a question
already answered).

**Price PSF is derived, not typed** — price ÷ sqft, read-only. It is a quotient, and a field
for it is only a way for the two to disagree. The import treats it the same way and stores it
nowhere.

**Deposit and Second Payment become real installments** on the sale's existing payment
schedule, **created due, not paid**. The form asks when a payment is *dated*; it does not ask
whether the money arrived, and recording cash as received on that basis is a claim the person
filling it in never made. Marking paid is one click on the schedule.

Broker is a picker rather than the import's free-text name match: a spreadsheet has no ids,
but here the real broker is one click away and a typo would produce no attribution at all.

## 7. A sale could never reach Closed

**The most serious find of the day.**

The Closed gate refuses a sale whose Deed, NOC and Possession Certificate are not attached,
and tells you to *"upload them to the sale's documents, then move the stage"*. **There was no
such place.**

The gate counts `document.saleId`. `UploadDocumentDto` had no `saleId` field,
`DocumentsService.create()` never wrote one, and `GET /documents` could not even list by sale.
**The column the gate reads could not be set by any route in the application.** Every sale in
the system was permanently one step from closing, and Sales could read exactly why a deal
would not close and do nothing whatsoever about it.

**Now:**

- `saleId` is accepted on upload and listable.
- A sale-attached document is **also attached to that sale's unit and project**. The columns
  are independent, not exactly-one-of, and this is the case that needs both: a Deed is
  evidence about the deal (what the gate asks) and about the unit (what whoever opens the unit
  next year asks, not knowing which sale it arrived on). Filed in one place only, the other
  audience never finds it.
- The unit and project are **derived from the sale**, not trusted from the caller — a
  mismatched `unitId` would file a Deed against the wrong unit, and the sale already knows.
- Reading is scoped to `saleId` alone. A unit that sold twice must not let the first deal's
  Deed answer for the second.
- The upload rows live **in the Edit Sale dialog**, one per required category, appearing only
  when the chosen stage owes something, charged **per rung crossed** (already Under Contract →
  Closed owes three documents, not five).

*Verified end to end:* with all three attached, the refusal changes from the document gate to
the **discount** gate — a different guard, correctly still standing.

### What still gates a Closed sale

1. The sale must exist first — a sale cannot be born closed, because documents attach to a
   sale that exists.
2. Deed + NOC + Possession Certificate on that sale (cumulative if stages are skipped:
   Prospect → Closed also owes LOI and Booking Agreement).
3. Discount approval if the price is more than the org threshold (default **5%**) below
   asking.
4. `buyerType` decides the sitting tenant's fate: `SITTING_TENANT` ends the tenancy,
   `THIRD_PARTY` transfers it intact.

Closing the sale is what flips the unit to SOLD. Setting `Unit.status = SOLD` by hand
bypasses all four — and `LEASED → SOLD` is not even a legal manual transition
(`units.service.ts` `STATUS_TRANSITIONS`); only SUPER_ADMIN/FOUNDER can override.

## 8. Deployment

The scp/ssh deploy job was replaced with a keyless SSM one. It **could never have worked**:
port 22 was open to a single home IP and hosted runners get a different address every run.

See **`docs/DEPLOY_SSM_SETUP.md`** for the full runbook. Short version: 2 secrets, up to 4
variables, one `production` environment, and `enable_github_deploy=true` in Terraform.
`EC2_HOST`, `EC2_SSH_KEY` and `GH_DEPLOY_TOKEN` are no longer needed at all.

**This release is on `main` but is NOT deployed.** `DEPLOY_ENABLED` is unset, so CI ran and
the deploy job skipped, as it has for 30+ pushes.

## 9. Known gaps left open

- **Live-record deletion does not release the unit.** By design, and the dialog says so — but
  it means a deleted lease leaves a unit reading `LEASED`. The history banner will flag it.
- **The stage library will surface typos.** Mitigated by usage counts, not prevented. A
  locked, admin-managed catalogue is a different build.
- **No admin screen for the stage library.** Labels are added by using them.
- **Leases on SOLD units are still excluded from billing.** Deliberate; blocked on the five
  open questions in `SALE_ON_TENANTED_UNIT_SPEC.md`.
- **Concurrent-session work left uncommitted.** A second session was editing this repo during
  this work (R11 import corrections): `lease-import.service.ts` + spec, `api.ts`,
  `api.test.ts`, `authStore.ts`, `RentHistoryImportPage.tsx`, `SaleHistoryImportPage.tsx`,
  `sales.controller.ts`. Deliberately **not** merged. One exception: ~9 lines of that work
  ride along in `useApi.ts` in commit `b40bd54`, because separating them would have meant
  reverting it.
